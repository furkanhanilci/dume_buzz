Commissioning harness · operations

DUM-E Operations

How to run the harness that builds AETHRION — the pipeline, the runtimes it is allowed to use, and the one thing it will never let you do.

Invariant

What DUM-E is

DUM-E is a commissioning harness. It takes a frozen work package, assembles a cohort of roles, gives each role a runtime it has been measured to be fit for, isolates the work in a worktree, and then refuses to call it done until three independent stages say so.

Nothing accepts a package on the strength of a claim. Not a message, not a reaction, not a model saying it passed. Every verdict is recorded through the state store by an identity the store checks for independence, and the gate reads the store.

This matters most now that DUM-E is visible inside Buzz. Buzz shows, routes, launches and notifies. It cannot decide that a package passed.

Sequence

What one run actually does

The order is load-bearing: each stage is gated on the one before it, so a failure names the stage that produced it rather than surfacing at the end.

  1. packet — the frozen work package, carried whole rather than summarised
  2. cohort — which roles this package needs, and what each must not share with the others
  3. runtime binding — a qualified runtime per role, families kept apart
  4. worktree — an isolated view; protected paths are unwritable by construction
  5. plan — the architect's plan, before any code exists
  6. RED — tests written first, and observed failing
  7. GREEN — implementation, and the same tests observed passing
  8. spec review — against the frozen specification, by a different family
  9. code review — the diff, by a third identity
  10. fresh verification — a session with no producer history
  11. gate — deterministic; reads records, not opinions
MERGE_ELIGIBLE is not ACCEPTED. The machine gate says the work survived every stage. Acceptance is a human and AETHRION decision, recorded separately.

Measured

Runtimes, and why four families

A runtime may hold a role only after it has answered live trials — tool calling, structured output, refusing an unsound claim, admitting uncertainty. Being installed is not qualification; a CLI on PATH says a file exists, a trial says the runtime answered.

The binder then spreads the cohort so that no reviewer shares a model family with the implementer. One family cannot review its own work: it shares its own blind spots.

Four distinct families, every independence rule satisfied. To re-derive this binding at any time:

python3 -m dume.cli runtime --probe        # measure what can run here
python3 -m dume.cli qualify <runtime> --record
python3 -m dume.cli runtime --bind <role>
Qualification spends real requests. That is the point — quota and auth cannot be established without it, so a probe alone can only ever answer UNKNOWN for a CLI-backed runtime.

Operating

Running the harness

Everything is reached through one command line. Each subcommand either reports a measured fact or refuses.

Look before you touch

python3 -m dume.cli status              # every package and its state
python3 -m dume.cli status --wave 4
python3 -m dume.cli show WP-003         # one package in full
python3 -m dume.cli history WP-001      # every transition, with actors
python3 -m dume.cli health              # is this deployment usable

Rehearse before you commit

python3 -m dume.cli pilot -v            # synthetic end-to-end, throwaway state
python3 -m dume.cli live WP-003         # real models, synthetic repo
python3 -m dume.cli reliability         # repeat a live run, report the spread
python3 -m dume.cli scenarios -v        # the adversarial acceptance scenarios

Commission for real

python3 -m dume.cli commission WP-003   # real state, real target repo, live models
python3 -m dume.cli evidence WP-003     # what was recorded, and by whom
An implementing actor cannot accept its own package. transition takes --actor, and the store refuses a verdict from the identity that produced the candidate. This is the wall a run stops at, and it is not a bug.

Closed grammar

Talking to DUM-E

There is no shell. Every instruction is parsed against a fixed vocabulary and converted into a typed intent — the same path whether it arrives from the terminal or, later, from a Buzz channel.

python3 -m dume.cli command --vocabulary
python3 -m dume.cli command "show WP-003" --actor otonom
ClassCommands
READ status · show · history · evidence · findings · next · open · read · roles · runtimes · spaces · ask · commands
CONTROL commission · pause · challenge · enable · disable · reserve · release
English prose is never a command. PASS, ACCEPTED, MERGE_ELIGIBLE, pasted JSON and reactions create no state anywhere — in the terminal or in a channel.

When a runtime runs out

Quota is not a property of the work. quota-watch.py reports exhaustion to the registry and asks DUM-E's binder what the role gets instead — it never picks the replacement, and when nothing eligible is left the role waits rather than taking whatever remains.

./quota-watch.py              # one pass
./quota-watch.py --watch 60   # keep checking
